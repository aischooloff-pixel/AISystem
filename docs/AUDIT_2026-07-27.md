**1. [КРИТИЧНО] Правило смещения существует только как текст промпта**

ТЗ (Блок 4, «Три дополнительные оси»): «клиент с признаками `warm`, но высокой
срочностью и высокой готовностью → переводится в `hot` и передаётся Юлии».

В коде решение о передаче принимается так ([qualification.py:238](bot/handlers/qualification.py:238)):

```python
if qualification.get("needs_yulia") or status == "hot":
```

Если модель вернула `status="warm"`, `readiness="high"`, `urgency="high"` и
`needs_yulia=false` — клиент **остаётся warm и Юлии не передаётся**. Детерминированное
правило ТЗ отдано на усмотрение вероятностной модели. Просьба соблюдать правило
есть в промпте ([qualifier.py:37](bot/prompts/qualifier.py:37)), но это просьба, а не гарантия.

Теста на это правило в наборе нет — проверено поиском по `tests/`.

**Цена ошибки ровно та, которой вы опасаетесь: горячий клиент молча остаётся в
прогреве и до Юлии не доходит.**

**Фикс** — постправило рядом с порогом 85 в `AIClient.qualify` ([ai.py:243](bot/services/ai.py:243)),
чтобы оно действовало независимо от того, какой хендлер вызвал квалификацию:

```python
if (
    data.get("status") == "warm"
    and data.get("readiness") == "high"
    and data.get("urgency") == "high"
):
    # «Правило смещения» (ТЗ, Блок 4): детерминированное требование,
    # его нельзя оставлять на усмотрение модели.
    data["status"] = "hot"
    data["needs_yulia"] = True
    data.setdefault("needs_yulia_reason", "Правило смещения: warm при высокой готовности и срочности")
```

**2. [ВАЖНО] `utm` не захватывается ни в одном сценарии**

ТЗ, Часть 3, «Что фиксируется при первом касании»: «источник · дата · ссылка ·
**UTM-метка (если есть)** · первое действие». Поле есть в схеме, но во всём коде
встречается только в проверке схемы `setup_airtable.py`.

Причина: deep link сверяется со справочником **целиком**
([start.py:159](bot/handlers/start.py:159)) — `param in VALID_SOURCES`. Параметр вида
`site_utm_spring2026` не распознаётся как источник и уводит клиента на кнопки
выбора, а метка теряется.

**Фикс** — разбирать параметр по разделителю:

```python
source, _, utm = param.partition("__")
if source in VALID_SOURCES:
    data = {"source": source}
    if utm:
        data["utm"] = utm
```

**3. [МЕЛОЧЬ] `next_action_date` не заполняется**

Поле есть в схеме, кодом не пишется. `next_step` пишется, дата — нет. Юлия не
увидит, к какому сроку запланировано следующее действие. Заполнять в
`_store_qualification` при постановке `next_step`.

**ВЕРДИКТ:** модель данных и большинство правил ТЗ реализованы точно, но одно
детерминированное правило квалификации отдано модели — это прямой риск потери клиента.

**6. [ВАЖНО] Стоп-фразы ловятся только дословно — 7 из 8 перефразировок прошли**

Результат подстановки:

```
ПРОПУЩЕНО 'Я гарантирую вам результат'          (вставлено одно слово)
ПРОПУЩЕНО 'Гарантирую результат'                (убрано «Я»)
ПРОПУЩЕНО 'Я гарантирую хороший результат'
ПРОПУЩЕНО 'Я точно знаю причину вашей проблемы'
ПРОПУЩЕНО 'Вы сами в этом виноваты'
ПРОПУЩЕНО 'После диагностики у вас всё изменится'
ПРОПУЩЕНО 'Без моей помощи вы просто не справитесь'
ПОЙМАНО   'Вам обязательно нужна диагностика прямо сейчас'
```

Формально ТЗ выполнено: требуется проверка `bot_response` на стоп-фразы, и
дословные она ловит. Но валидатор — вторая линия обороны, и рассчитана она
ровно на случай, когда модель нарушила инструкцию промпта. Модель, нарушающая
инструкцию, почти наверняка сформулирует **своими словами**, а не цитатой из
списка.

**Фикс** — добавить к дословному списку набор смысловых шаблонов:

```python
STOP_PATTERNS: tuple[re.Pattern, ...] = (
    re.compile(r"гарантиру\w*\b.{0,20}\bрезультат"),
    re.compile(r"\bвы\b.{0,15}\bсам\w*\b.{0,15}\bвиноват"),
    re.compile(r"без\s+моей\s+помощи.{0,20}не\s+справит"),
    re.compile(r"точно\s+знаю.{0,20}причин"),
    re.compile(r"после\s+(?:диагностики|работы).{0,25}(?:всё|все)\s+изменит"),
)
```

и проверять их в `find_stop_phrase` по уже нормализованному тексту. Ложное
срабатывание здесь дёшево — лишняя передача Юлии, что прямо соответствует
принципу безопасности ТЗ.

**ВЕРДИКТ:** валидатор строг и аккуратен по букве ТЗ, но пробивается
перефразированием — а именно так стоп-фраза и появится на практике.

## Раздел 13 — Открытые проблемы из DEPLOYMENT.md

**СТАТУС: ⚠️ ЗАМЕЧАНИЯ**

**1. Юлия не нажала `/start` — что именно заблокировано**

Telegram отвечает `PEER_ID_INVALID`. Заблокированы **все** исходящие к Юлии:

| Источник | Что не доходит |
|---|---|
| `notifier.py` | карточка клиента при передаче — **основной продукт системы** |
| `comments.py` (9 мест) | уведомления о потенциальных клиентах, предложенные ответы, подтверждения публикации |
| `pause_check.py` | пересылка сообщений переданных клиентов |
| `questionnaire.py` | предвстречный отчёт по анкете |
| `weekly_report.py` | еженедельный отчёт |
| `notify_backup.py` | результат бэкапа — **о сбое бэкапа она тоже не узнает** |
| `qualification.py` | уведомление о сбое AI |

Записи в Airtable при этом создаются исправно. Система копит данные и молчит.

**2. Восемь дублей в Posts — скрипт написан**

`scripts/dedup_posts.py`. Сухой прогон уже выполнен:

```
post_id=1080: записей 9 → 1
  оставляем rec4GADqwpyho9C6G (заполнено полей: 6)
  счётчики 1080: {'comments_count': 2, 'potential_clients_count': 4}
                → {'comments_count': 13, 'potential_clients_count': 9}
Итого: удалить 8, обновить счётчиков 1
```

Скрипт пересчитывает счётчики по фактическим строкам `Comments` (инкременты
разошлись по дублям, поэтому и у оставшейся записи они занижены) и предупреждает,
если в дубле есть поля, которых нет у оставляемой записи. Без `--apply` только
показывает план.

**3. `suggested_reply: null` — фикс в одну строку**

[validators.py:227](bot/utils/validators.py:227). Модель честно возвращает `null`,
когда сама же проставила `needs_reply: false`. Потребители значения к пустоте
готовы: `or '—'` в карточке, `or ""` при публикации. На живом трафике это
**23% комментариев**, ушедших на ручную передачу без повода.

```python
if "suggested_reply" in data and not isinstance(data["suggested_reply"], (str, type(None))):
```

**4. FSM в памяти — что теряется**

Точная позиция в анкете и номер вопроса сценария B. Не теряется: контакт,
история переписки, статус, все данные CRM — они в Airtable. `restore_after_restart`
продолжает диалог с определения сценария, клиент не остаётся в тишине.
**Для MVP некритично.** Redis — Спринт 2.

**5. Имя бота**

BotFather → `/setname` и `/setusername`. **Токен не меняется**, права бота в
канале и группе сохраняются, перенастройка не нужна. Сделать до прихода живых клиентов.

**ВЕРДИКТ:** все пять пунктов имеют готовое решение; четыре из пяти закрываются за час.
