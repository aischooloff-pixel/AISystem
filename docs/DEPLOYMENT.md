## 3. HTTPS и вебхук

Telegram не принимает вебхук по `http://`, а сертификаты выпускаются на имя,
а не на IP. Собственного домена к моменту развёртывания не было, поэтому взят
`nip.io` — публичный DNS, резолвящий `45.139.77.106.nip.io` в тот же адрес.
Аккаунт не нужен, Let's Encrypt имя принимает.

| | |
|---|---|
| Адрес вебхука | `https://45.139.77.106.nip.io/webhook` |
| Сертификат | Let's Encrypt, истекает **2026-10-25** |
| Автопродление | `certbot.timer`, активен |

**Это временное решение.** Переезд на настоящий домен описан в разделе 9.

Nginx проксирует наружу **единственный путь** `/webhook`, всё остальное
отдаёт 404 — сервер не отвечает на посторонние запросы. Сам вебхук защищён
секретным заголовком: POST без него получает `401`.

## 6. Найденные дефекты

### Гонка при параллельной доставке комментариев — исправлено

**Как проявилось.** При первом запуске Telegram выгрузил разом тринадцать
накопленных комментариев к одному посту. Aiogram обработал их параллельно,
каждый обработчик спросил «есть ли такой пост», все получили «нет» — и девять
создали запись. В `Posts` оказалось девять копий поста `1080`.

Тем же путём терялись инкременты счётчиков: обработчики читали одно и то же
значение и записывали одно и то же плюс один.

**Причина.** Классический read-modify-write race. У контактов пер-ключевой
`asyncio.Lock` стоял с самого начала — правило дедупликации в ТЗ помечено как
критичное. У постов такой защиты не было.

**Почему не поймали тесты.** Существовавший тест `test_posts_upsert_and_counters`
проверял только последовательные вызовы и оставался зелёным.

**Исправление.** Общий замок на `upsert_post` и `increment_post_counter` —
общий потому, что создать запись умеют оба. Добавлен параллельный тест;
проверено, что без замка он падает (`assert 1 == 4` — потерянные инкременты),
с замком проходит.

**Осталось прибрать:** восемь дублей в живой базе — см. раздел 7.

### Тесты, зависевшие от порядка запуска — исправлено

Одиннадцать тестов проверяли содержимое логов через `caplog`, который слушает
корневой логгер. Логгер `app` намеренно поднят с `propagate = False`, чтобы
записи не двоились в journalctl. В результате тесты, запущенные после файла,
поднимавшего логирование, молча ничего не проверяли — ложно-зелёный результат.

Добавлена фикстура `app_caplog`, вешающая обработчик прямо на нужный логгер.

## 7. Открытые проблемы

### Юлия не нажала `/start` — блокирует всё оповещение

**Самое важное в документе.**

Telegram запрещает боту писать первым тому, кто с ним не заговорил. Проверено
напрямую: API отвечает `PEER_ID_INVALID`. За час работы — **16 неудачных
попыток** отправить Юлии уведомление.

Следствие: бот исправно находит потенциальных клиентов и раскладывает их по
Airtable, но **не может об этом сообщить**. Не доходят карточки клиентов,
уведомления о комментариях, еженедельный отчёт.

**Решение:** Юлия открывает бота и нажимает `/start`. Десять секунд.

### Восемь дублей в Posts — нужно решение

Последствие исправленной гонки. Живых записей должно быть одна.

- **Оставить:** `rec4GADqwpyho9C6G` — в нём текст поста и ссылка.
- **Удалить:** восемь остальных, все беднее, уникальных данных не содержат
  (проверено сравнением полей).
- **Счётчикам** выставить правдивые значения: 13 комментариев,
  9 потенциальных клиентов. Сейчас там 2 и 4 — инкременты разошлись по дублям.

Удалить не удалось: защитный фильтр заблокировал операцию и через shell,
и через инструмент Airtable. Обходить не стал. Нужно либо разрешение,
либо удаление вручную.

### Валидатор `suggested_reply` строже, чем требуется — нужно решение

Три комментария из тринадцати ушли на ручную передачу Юлии, потому что модель
вернула `suggested_reply: null`. Значение честное — она сама же проставила
`needs_reply: false`, отвечать не на что.

При этом весь код ниже по течению к пустому значению готов: в карточке
`or '—'`, при публикации `or ""`. То есть проверка отбраковывает корректный
ответ модели и создаёт лишнюю ручную работу — на живом трафике это 23%
комментариев.

Ошибка **безопасная**: она передаёт решение человеку, а не боту. Поэтому
правка защитного контура ИИ отложена до явного согласования.

Чинится в одну строку: разрешить `None`, когда `needs_reply` равно `false`.

### FAQ — заглушка

`bot/knowledge/faq.md` — 43 строки вместо девяти разделов. Полный документ
у Юлии. Бот работает и без него, просто беднее отвечает на организационные
вопросы. Подкладывается файлом и рестартом сервиса, передеплой не нужен.

## 9. Эксплуатация

### Управление

```bash
systemctl status geikina-bot
systemctl restart geikina-bot
journalctl -u geikina-bot -f
```

Логи приложения — `/home/yulia/geikina-bot/logs/`. Их два, и это намеренно:
технический и отдельный аудит решений ИИ.

### Обновление кода

Локально:

```bash
git archive --format=tar.gz -o /tmp/geikina-bot.tar.gz HEAD
scp -i ~/.ssh/geikina_bot /tmp/geikina-bot.tar.gz root@45.139.77.106:/tmp/
```

На сервере:

```bash
tar xzf /tmp/geikina-bot.tar.gz -C /home/yulia/geikina-bot && chown -R yulia:yulia /home/yulia/geikina-bot && systemctl restart geikina-bot
```

### Переезд на настоящий домен

1. A-запись домена на `45.139.77.106`.
2. `certbot --nginx -d bot.домен.ru`
3. Заменить `server_name` в `/etc/nginx/sites-available/geikina-bot`.
4. Поправить `WEBHOOK_URL` в `.env` — бот переустановит вебхук сам при старте.
5. `systemctl restart geikina-bot`

Занимает пару минут. Проверить результат: `getWebhookInfo` должен показать
новый адрес и `pending_update_count: 0`.
