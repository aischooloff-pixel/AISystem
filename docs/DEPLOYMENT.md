Что реализовано по каждому блоку ТЗ, что развёрнуто, что сломано и что осталось.

`docs/SETUP.md` описывает, **как поднять систему с нуля**. `docs/USER_GUIDE.md` —

Спринт 1 — все тринадцать блоков ТЗ реализованы, протестированы и **развёрнуты
в бою**. Бот принимает живой трафик из канала Юлии, разбирает комментарии через

поэтому бот физически не может ей ничего отправить. Система собирает клиентов
и молчит об этом. Подробности в разделе 8.

### Блок 1 · Каркас и конфигурация — закрыт

Точка входа, конфиг, логирование, юнит systemd.

**Код:** `bot/config.py`, `bot/main.py`, `bot/utils/logger.py`, `bot/texts.py`,
`systemd/geikina-bot.service`, `.env.example`, `requirements.txt`.

Конфигурация читается через `pydantic-settings` и **падает на старте** с
перечнем недостающих переменных, а не в рантайме посреди диалога с клиентом.
Секреты не имеют значений по умолчанию — это осознанно: пустая строка прошла бы
валидацию `str`, и бот сломался бы позже и непонятнее.

Логгеров два и они независимы: технический `app` и отдельный аудит решений ИИ.
У `app` выставлен `propagate = False`, чтобы записи не двоились в journalctl —
эта деталь позже стоила одиннадцати молча непроверяющих тестов, см. раздел 7.

**Тесты:** `test_block1_smoke.py` — 7.

### Блок 2 · База знаний — реализован, **не закрыт**

Восемь `.md`-файлов с материалами бренда, загрузка и выдача их в промпт.

**Код:** `bot/services/knowledge.py`, `bot/knowledge/*.md` (1 807 строк).

Файлы: `brand`, `products`, `communication`, `objections`, `qualification`,

алфавитном порядке с заголовками «## Источник: {файл}» — чтобы модель могла
сослаться на источник. Оценка объёма пишется в лог, при превышении 100 000
токенов — предупреждение. Сейчас ~16 300 токенов, запас шестикратный.
Новый `.md` подхватывается без изменения кода.

Дословность переноса из PDF/DOCX Юлии сверялась отдельной проверкой по каждому
из шести переносимых файлов.

**Принятые решения по ходу:**

  нет. Сработало правило ТЗ «ориентируйся на факт».
- `templates.md`: тексты из ТЗ перенесены дословно и помечены «из ТЗ»; шаблоны,
  которых в ТЗ не было (нецелевой, прогрев, нет информации), написаны по
  алгоритмам документов и **помечены «на утверждение Юлией»**.

**Почему не закрыт.** `faq.md` — 43 строки вместо девяти разделов. Документ
«FAQ бренда v1.0» заказчиком не передан; собрана базовая версия из раздела 18
«Базы знаний» плюс обязательные правила из ТЗ, в шапке файла стоит явная
пометка «НЕПОЛНАЯ ВЕРСИЯ». Формальный критерий «все 8 файлов на месте» выполнен,
критерий дословности — нет.

**Тесты:** `test_block2_knowledge.py` — 11.

### Блок 3 · Airtable — закрыт

Слой доступа к CRM: CRUD по шести таблицам, дедупликация, retry, rate limit.

**Код:** `bot/services/airtable.py` (~680 строк), `scripts/setup_airtable.py`.

Ключевое — **дедупликация по `telegram_id`**, в ТЗ помечена как критичная. Пара
«поиск → создание» защищена пер-пользовательским `asyncio.Lock`: два
одновременных апдейта одного человека (двойной тап по кнопке) без замка создали
бы дубль. **При сбое поиска запись не создаётся вообще** — лучше пропустить,
чем задвоить.

Retry с нарастающими паузами на 429 и 5xx, ограничение частоты через семафор на
5 одновременных запросов. Запись идёт с `typecast: True` — Airtable сам
приводит значения к типам полей.

`scripts/setup_airtable.py --check` сверяет фактическую схему базы с ожидаемой
и печатает, чего не хватает.

**Тесты:** `test_airtable.py` — 21, `test_dedup.py` — 7,
`test_setup_airtable.py` — 6.

### Блок 4 · Промпты и слой ИИ — закрыт

**Код:** `bot/prompts/` (`system_prompt`, `qualifier`, `comment_analyzer`,
`scenario_detector`, `questionnaire_analyzer`), `bot/services/ai.py`,
`bot/utils/validators.py`.

Каждый ответ модели проходит **валидацию по схеме**: неверный тип или
отсутствующее поле — одна повторная попытка, затем передача Юлии. ИИ не решает
за человека, если сам себе не доверяет: при `confidence` ниже 85 решение уходит
Юлии (порог из документа «Критерии квалификации», задаётся конфигом).

Отдельно — **перехват стоп-фраз**: если модель в ответе клиенту употребила
запрещённую формулировку, ответ заменяется. Проверена устойчивость к инъекции
в промпт через тройные кавычки.

Модель заменяема через `OPENAI_MODEL` без правки кода.

**Тесты:** `test_ai.py` — 32.

### Блок 5 · `/start`, deep links, источник — закрыт

**Код:** `bot/handlers/start.py`.

Все deep links определяют источник (15 значений: канал, комментарий, личка, VK,
сайт, рекомендация, мастермайнд, выступление, QR и другие). Новый контакт
заводится в `Contacts` плюс касание в `Touches`. Повторный `/start` **не создаёт
дубль** и не переопределяет источник первого касания. Без deep link
показываются кнопки выбора. Приветствие содержит представление ИИ-помощником —
требование ТЗ, бот не выдаёт себя за Юлию.

Клиент, уже переданный Юлии, **не запускает автоматику** — приоритет решения
человека над ботом.

**Тесты:** `test_block5_start.py` — 18.

### Блок 6 · Квалификация — закрыт

Сердце системы: FSM трёх сценариев и передача Юлии.

**Код:** `bot/handlers/qualification.py`, `bot/services/notifier.py`,
`bot/states.py`, `scripts/check_timeouts.py`.

- **Сценарий A** (готов покупать) — два вопроса и передача.
- **Сценарий B** (описал проблему) — до пяти вопросов, с досрочным завершением,
  когда картина ясна раньше.
- **Сценарий C** (информационный запрос) — ответ без квалификации, с
  переключением на B, если разговор повернул к проблеме.

Вопросы задаются **по одному**, не списком. Карточка Юлии содержит восемь
блоков плюс timeline касаний и кнопки действий. Реализованы все четыре
маршрута; `confidence < 85` даёт автоматическую передачу.

Таймауты (`check_timeouts`, ежечасно): 24 часа — одно мягкое напоминание,
72 часа — перевод в `cold` с пометкой «нет ответа», 7 дней — задача Юлии
«решить: прогрев или закрытие».

**Тесты:** `test_block6_qualification.py` — 18.

### Блок 7 · Панель Юлии — закрыт

**Код:** `bot/handlers/callbacks.py`, `bot/handlers/admin.py`,
`bot/middlewares/pause_check.py`.

Четыре кнопки карточки — «Беру», «Прогрев», «Нецелевой», «Пауза» — обновляют
CRM, после нажатия сообщение редактируется, чтобы не жать дважды. Пятнадцать
admin-команд плюс `/cancel`. Команды недоступны обычным пользователям —
проверено отдельным тестом.

Middleware паузы **полностью останавливает автоматику** по клиенту: сообщения
переданного Юлии человека сохраняются и пересылаются ей, но бот в разговор не
вмешивается.

**Тесты:** `test_block7_admin.py` — 16.

### Блок 8 · Мониторинг комментариев — закрыт

## 4. HTTPS и вебхук

Telegram не принимает вебхук по `http://`, а сертификаты выпускаются на имя,
а не на IP. Домена к моменту развёртывания не было, поэтому взят `nip.io` —
публичный DNS, резолвящий `45.139.77.106.nip.io` в тот же адрес. Аккаунт не
нужен, Let's Encrypt имя принимает.

| | |
|---|---|
| Адрес вебхука | `https://45.139.77.106.nip.io/webhook` |
| Сертификат | Let's Encrypt, истекает **2026-10-25** |
| Автопродление | `certbot.timer`, активен |

**Это временное решение**, переезд описан в разделе 10.

Nginx проксирует наружу **единственный путь** `/webhook`, остальное отдаёт 404.
Сам вебхук защищён секретным заголовком: POST без него получает `401`.

## 6. Что сделано при развёртывании

1. Проверена достижимость OpenAI, Telegram и Airtable **с самого сервера** до
   начала установки — чтобы не разворачивать систему там, где она не заработает.
2. Отключён парольный вход, заблокирован скомпрометированный root-пароль,
   поднят файрвол.
3. Установлены Python-окружение, nginx, certbot, git.
4. Заведён служебный пользователь, развёрнут код, собрано виртуальное окружение.
5. Выпущен сертификат, настроено проксирование только вебхука.
6. Поднят `systemd`-юнит с автоперезапуском.
7. Поставлены cron-задачи: таймауты ежечасно, отчёт по понедельникам 10:00 МСК,
   бэкап по воскресеньям 03:00 МСК. Запуск `check_timeouts` проверен вручную.
8. Пересоздана база Airtable в рабочем workspace, схема сверена скриптом.

Код заливается архивом `git archive`: репозиторий приватный, а прав добавить

## 7. Найденные дефекты

### Гонка при параллельной доставке комментариев — исправлено

**Как проявилось.** При первом запуске Telegram выгрузил разом тринадцать
накопленных комментариев к одному посту. Aiogram обработал их параллельно,
каждый обработчик спросил «есть ли такой пост», все получили «нет» — и девять
создали запись. Тем же путём терялись инкременты счётчиков.

**Причина.** Read-modify-write race. У контактов пер-ключевой замок стоял
изначально — правило дедупликации в ТЗ помечено критичным. У постов такой
защиты не было.

**Почему не поймали тесты.** Существовавший тест проверял только
последовательные вызовы и оставался зелёным.

**Исправление.** Общий замок на `upsert_post` и `increment_post_counter` —
общий потому, что создать запись умеют оба. Добавлен параллельный тест;
проверено, что без замка он падает, с замком проходит.

### Тесты, зависевшие от порядка запуска — исправлено

Одиннадцать тестов проверяли логи через `caplog`, слушающий корневой логгер,
тогда как логгер `app` намеренно поднят с `propagate = False`. Тесты,
запущенные после файла, поднимавшего логирование, **молча ничего не
проверяли** — ложно-зелёный результат. Затрагивало критерии Блоков 3–4: retry
на 429, живучесть при обрыве сети, перехват стоп-фразы, логирование операций.

Исправлено фикстурой `app_caplog`; прогон проверен в трёх разных порядках.

## 8. Открытые проблемы

### Юлия не нажала `/start` — блокирует всё оповещение

**Самое важное в документе.**

Telegram запрещает боту писать первым тому, кто с ним не заговорил. Проверено
напрямую: API отвечает `PEER_ID_INVALID`. За час работы — **16 неудачных
попыток** отправить Юлии уведомление.

Следствие: бот находит потенциальных клиентов и раскладывает их по Airtable,
но **не может об этом сообщить**. Не доходят карточки клиентов, уведомления о
комментариях, еженедельный отчёт.

**Решение:** Юлия открывает бота и нажимает `/start`. Десять секунд.

### Восемь дублей в Posts — нужно решение

Последствие исправленной гонки.

- **Оставить:** `rec4GADqwpyho9C6G` — в нём текст поста и ссылка.
- **Удалить:** восемь остальных, уникальных данных не содержат (проверено
  сравнением полей).
- **Счётчикам** выставить 13 комментариев и 9 потенциальных клиентов; сейчас
  2 и 4, инкременты разошлись по дублям.

Удалить не удалось: защитный фильтр заблокировал операцию и через shell, и
через инструмент Airtable. Обходить не стал.

### Валидатор `suggested_reply` строже, чем требуется — нужно решение

Три комментария из тринадцати ушли на ручную передачу Юлии, потому что модель
вернула `suggested_reply: null`. Значение честное — она сама же проставила
`needs_reply: false`, отвечать не на что.

Весь код ниже по течению к пустому значению готов: в карточке `or '—'`, при
публикации `or ""`. То есть проверка отбраковывает корректный ответ модели и
создаёт лишнюю ручную работу — на живом трафике это 23% комментариев.

Ошибка **безопасная**: она передаёт решение человеку, а не боту. Поэтому правка
защитного контура ИИ отложена до согласования. Чинится в одну строку.

### FSM в памяти — ограничение, признанное осознанно

Состояния диалога хранятся в `MemoryStorage`. При рестарте точная позиция в
анкете теряется, но **клиент не остаётся в тишине**: `restore_after_restart`
продолжает разговор с определения сценария. Redis — кандидат в Спринт 2.

## 10. Эксплуатация

### Управление

```bash
systemctl status geikina-bot
systemctl restart geikina-bot
journalctl -u geikina-bot -f
```

Логи приложения — `/home/yulia/geikina-bot/logs/`, их два: технический и
отдельный аудит решений ИИ.

### Обновление кода

Локально:

```bash
git archive --format=tar.gz -o /tmp/geikina-bot.tar.gz HEAD
scp -i ~/.ssh/geikina_bot /tmp/geikina-bot.tar.gz root@45.139.77.106:/tmp/
```

На сервере:

```bash
tar xzf /tmp/geikina-bot.tar.gz -C /home/yulia/geikina-bot && chown -R yulia:yulia /home/yulia/geikina-bot && systemctl restart geikina-bot
```

### Переезд на настоящий домен

1. A-запись домена на `45.139.77.106`.
2. `certbot --nginx -d bot.домен.ru`
3. Заменить `server_name` в `/etc/nginx/sites-available/geikina-bot`.
4. Поправить `WEBHOOK_URL` в `.env` — бот переустановит вебхук сам при старте.
5. `systemctl restart geikina-bot`

Проверка: `getWebhookInfo` должен показать новый адрес и `pending_update_count: 0`.

### Проверка живости

```bash
python -m scripts.setup_airtable --check   # структура CRM
python -m pytest tests/                    # 219 тестов
```

Чек-лист ручной проверки после деплоя — `docs/SETUP.md`, раздел 8.
